# 京台科技项目承诺账

保存科技合作从接洽、签约到资源投入的证据关系，并为项目专员提供承诺管理后台。

## 领域资料

仓库中的 `contracts/context.schema.json` 描述基础资料格式，`fixtures/context.json` 给出可公开使用的示例。代码库只负责读取与校验这些资料，业务服务可沿用相同标识和版本约定。

当前资料反映的事实包括：

- 论坛包含项目签约
- 合作涉及多类科技产业
- 企业需对接科研资源和应用场景

## 承诺管理后台

`src/` 下是面向京台科技项目专员的承诺管理后台，覆盖半导体、生物电子、金融服务、软件研发四类合作，分别管理台企能力、北京科研资源、场景需求、尽调材料、签约版本与里程碑。

### 核心规则

- **五阶段分开统计**：接洽、签约、资源投入、验证完成、订单形成各自计数，复盘页（`GET /review`）中每个数字可下钻到责任主体、适用范围、前置条件与相应证据；每条承诺登记时就必须声明履约证据，"交换过名片"无法包装成合作成果。
- **确认完整才执行**：意向须全部参与方按同一版本号确认后才为"确认完整"，只有确认完整的意向才能进入执行。
- **撤回只终止后续动作**：撤回把未完成承诺标记为终止，已履约承诺与全部历史事件保留，半年后的复盘仍可核实经过。
- **版本变化显式声明影响**：新签约版本必须列出影响哪些未完成承诺（只能引用未完成承诺）；激活时被影响的承诺标记为"被取代"并记录在事件日志。
- **商业秘密按参与方隔离**：尽调材料与受限证据按可见名单隔离，无权查看者在复盘中只能看到脱敏引用（编号、类型、哈希），项目专员也不例外。
- **不得产生两个有效版本**：重复项目按归一化键去重；同一项目同一时间只有一个进行中的意向版本，确认与激活均采用版本号比较并交换，多方同时提交时只有一个生效。

### 运行

```bash
npm start          # 加载 fixtures/seed.json 样例项目并监听 :3000
npm test           # 全部领域规则与 HTTP 测试
```

### 主要接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/review?asParty=<partyId>` | 复盘页：五阶段统计与下钻，按身份隔离商业秘密 |
| POST | `/projects` | 立项（同键去重，返回 `deduplicated`） |
| POST | `/projects/:id/intents` | 起草意向（`supersede` 替换未确认版本） |
| POST | `/intents/:id/confirm` | 参与方按版本号确认（幂等） |
| POST | `/intents/:id/start-execution` | 进入执行（须确认完整） |
| POST | `/intents/:id/withdraw` | 撤回意向 |
| POST | `/commitments/:id/fulfill` | 登记履约（校验证据类型齐备） |
| POST | `/projects/:id/contracts` | 起草签约版本（`affects` 声明影响的未完成承诺） |
| POST | `/contracts/:id/activate` | 激活（`expectedValidVersion` 比较并交换） |
| GET | `/projects/:id/history` | 项目全部事件，供半年后核实 |
| POST | `/capabilities` `/research-resources` `/scenario-demands` `/due-diligence` `/evidence` `/projects/:id/milestones` | 六类资料登记 |

错误码映射：`VALIDATION→400`、`NOT_FOUND→404`、`FORBIDDEN→403`、`CONFLICT→409`、`INVALID_STATE→422`。

## 本地校验

运行项目自带测试即可确认样例资料可读取，且领域标识与版本字段完整。所有示例均为虚构数据，不含真实个人信息、账号或访问凭据。
